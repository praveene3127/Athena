# ATHENA — Architecture Decisions Log (DECISIONS.md)

1. **Target Platform Architecture:** Strictly adhering to `CLAUDE.md`: Athena is an **Android mobile application** built in **Flutter** (`app/`) communicating with a local **FastAPI** backend (`backend/`) on the laptop over USB port forwarding (`adb reverse tcp:8000 tcp:8000`).
2. **Screenshot-led UI Direction:** Follow the supplied Paytin mobile-app reference for a warm light canvas, vivid lime actions, rounded surfaces, generous spacing, dark ink accents, and a compact bottom navigation, adapted to Athena's reading and document workflows. The screenshot-to-code repository informs visual decomposition; its generated web stacks are ported into native Flutter widgets.
3. **Design System Tokens:** Use a warm off-white background (`#F4F5F0`), white cards, dark ink text, neon lime (`#C8F36A`) for primary actions, warm paper source blocks, and teal accents for verified AI context. Use soft rounded cards and a clear hierarchy modeled on the supplied reference.
4. **Agent Skills Engine (`skills.sh`):** Integrated `https://www.skills.sh/` as the continuous on-demand skills engine. Installed `flutter/agent-plugins` (architecture, layout, testing) and `addyosmani/agent-skills` (spec-driven, task breakdown, testing). Additional skills will be discovered and pulled dynamically as complex tasks arise.
5. **Lossless Chunker Invariant:** Reading chunks are created strictly by slicing canonical text character offsets `canonical_text[start:end]` to preserve 100% fidelity; string splitting and rejoining is prohibited.
6. **4-Way Integrity Guarantee:** A document is only marked `ready` if: joined chunks == canonical text, offsets are contiguous from 0 to len, slice identity holds for all chunks, and SHA-256 checksums match.
7. **Database Concurrency:** SQLite in WAL mode (`PRAGMA journal_mode=WAL; PRAGMA busy_timeout=5000;`) with distinct database sessions per request and background worker thread.
8. **Deterministic Offline Replay:** All Wikipedia REST responses (including negative hits) are cached on local disk (`data/cache/wiki/{sha1}.json`) with a custom `User-Agent`.
9. **Zero-Key Degradation:** Extractive mode (verbatim Wikipedia excerpts) is the default; LLM features (rewrite & Ask) require `LLM_API_KEY` and degrade gracefully with clear user messaging when unconfigured.
10. **Lossless Reader & Paper Aesthetic:** Source reading chunks are rendered in warm paper blocks with serif text using `ScrollablePositionedList`. Grounded AI context cards use a pale teal surface and teal accents to remain distinct from source text.
11. **Card Spacing & Verification Gate:** Minimum gap between context cards is strictly maintained at $\ge 3$ chunks, with a maximum of 8 cards per document. Source chunk checksums are cryptographically proven invariant before and after card generation.
12. **3-Chunk Sliding Ask Window:** The `/api/ask` endpoint constructs a localized sliding context window containing `<passage>` and previous/next `<neighbors>` with a 12 req/min rate limit and 5 standardized status envelopes.
13. **Resilient Background Execution:** A single-worker `ThreadPoolExecutor` queues one PDF job at a time and runs each job in a spawned child process. A hard worker failure is recorded as a retryable resource error while FastAPI stays alive; backend restarts recover stale jobs as `INTERRUPTED`.
14. **11-Stage Structural Extraction & Verification Pipeline:** To overcome PDF heuristic extraction limits and font map corruption, extraction implements an 11-stage pipeline: (0) Page Triage (classifying digital, scanned, hybrid, broken-font and grading A-D); (1) Structured span capture (font, size, weight, bbox); (2) Deterministic character repair mapping C1 controls (U+0080–U+009F) via CP-1252, targeted ligature expansion, and explicit invisible character rules recorded in an immutable `RepairLedger` with replay verification; (3) Reading order gutter and multi-column detection with spanning elements prioritized; (4) Relative block typing against document modal body font size and outline bookmarks (`doc.get_toc()`) with protected headings immune from header suppression; (5) Paragraph reconstruction combining indent, vertical line gaps, line width, terminal punctuation, and lowercase continuation across page breaks, with vocabulary-aware de-hyphenation; (6) Canonical text assembly with offset index and abbreviation-guarded sentence boundaries; (7) Page quality grading A-D; (8) Scored-boundary chunking with atomic heading glue; (9) 8-point cryptographic integrity verification; (10) Fallback ladder; and (11) Deterministic chunk IDs.
15. **Adaptive Reading Feed Boundaries:** A deterministic profile of paragraph lengths and local continuation cues targets a steady short reading interval. Headings stay with their opening passage; oversized paragraphs split at guarded sentence boundaries. The planner chooses canonical offsets only and fails if coverage is not contiguous. It does not claim semantic understanding or reorder author text.
16. **Confidence-aware PDF Reading Order:** With a supported gutter, blocks are read top-to-bottom within each column, and full-width blocks separate vertical bands. Ambiguous geometric overlap is surfaced as `reading_order_uncertain`; readers can inspect the source page. This remains a heuristic, not guaranteed perfect layout understanding.
17. **Book Upload Size:** Book PDFs have no arbitrary app-level byte or page cap. Both browser picker and backend upload use streams; jobs run sequentially with per-page progress. Real capacity is bounded by local disk and memory, and resource failures leave the document retryable instead of taking down the API.
